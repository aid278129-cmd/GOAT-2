======================================================================
1. PURPOSE OF THIS DOCUMENT
======================================================================

This document explains exactly what must be done to bring the current
Multi-Camera Indian ANPR Traffic Intelligence Platform into close alignment
with the complete problem statement.

The current project already contains a strong working base:
- Multi-camera WebRTC streaming
- Socket.io signaling
- Node.js backend
- Python FastAPI ANPR microservice
- YOLO-based plate detection
- Plate rectification
- PaddleOCR / PP-OCRv4
- Multi-frame voting
- Indian registration validation
- Detection history
- GIS route visualization using Leaflet
- Watchlist / BOLO alerts
- Mobile-camera pairing

Therefore, the solution described below DOES NOT require rebuilding the project
from scratch.

The objective is to extend the current system while preserving the existing
working ANPR pipeline.

The most important remaining work is:

2. Improved trajectory metadata
3. Traffic density analytics
4. Average speed estimation
5. Origin-Destination analytics
6. Route density analytics
7. Congestion detection

7. MODULE 2 - IMPROVE TRAJECTORY RECONSTRUCTION
======================================================================

The project already performs trajectory tracking.

The next step is to enrich each trajectory with useful metadata.

----------------------------------------------------------------------
7.1 Vehicle Search
----------------------------------------------------------------------

User searches:

TN45AB1234

Backend retrieves every detection matching this plate.

Sort by:

timestamp ASC

Example:

09:05 - CAM_01
09:18 - CAM_05
09:33 - CAM_09
09:48 - CAM_14

----------------------------------------------------------------------
7.2 Return Complete Trajectory Information
----------------------------------------------------------------------

For every point return:

- Camera ID
- Camera name
- Timestamp
- Latitude
- Longitude
- Direction
- OCR confidence
- Vehicle type
- Distance from previous camera
- Time from previous camera
- Estimated average speed

Suggested API:

GET /api/trajectory/TN45AB1234

Suggested response:

{
  "plate": "TN45AB1234",
  "totalSightings": 4,
  "totalDistanceKm": 11.4,
  "totalTravelTimeMinutes": 43,
  "points": [...]
}

----------------------------------------------------------------------
7.3 Calculate Distance Between Camera Points
----------------------------------------------------------------------

Use the Haversine formula or geographic library.

Input:

latitude1
longitude1
latitude2
longitude2

Output:

distanceKm

This can be calculated in Node.js.

No new AI model is required.

----------------------------------------------------------------------
7.4 Calculate Estimated Average Speed
----------------------------------------------------------------------

For two consecutive camera detections:

speed = distance / time

Example:

Distance = 3 km
Time = 5 minutes

speed = 3 / (5 / 60)
speed = 36 km/h

Store this only as an estimated segment speed.

IMPORTANT:

Do not describe this as exact instantaneous vehicle speed.

It is an estimated average speed between two geographically known camera
detections.

======================================================================
9. MODULE 4 - AVERAGE SPEED ANALYTICS
======================================================================

Average speed can be calculated from matched plates detected by two cameras.

----------------------------------------------------------------------
9.1 Required Data
----------------------------------------------------------------------

Plate
Camera A timestamp
Camera B timestamp
Camera A location
Camera B location
Distance between cameras

----------------------------------------------------------------------
9.2 Algorithm
----------------------------------------------------------------------

For every plate seen by Camera A and later by Camera B:

travelTime = timestampB - timestampA

averageSpeed = cameraDistance / travelTime

Ignore invalid results.

Example invalid conditions:

- negative travel time
- zero time difference
- unrealistic calculated speed
- detections separated by excessively large time intervals

Use configurable validation.

Example:

maxReasonableSpeed = 180 km/h

This prevents corrupted data from affecting analytics.

----------------------------------------------------------------------
9.3 API
----------------------------------------------------------------------

GET /api/analytics/speed

Example output:

{
  "route": "CAM_01 -> CAM_05",
  "averageSpeedKmh": 28.5,
  "vehicleCount": 114,
  "period": "10:00-11:00"
}

11. MODULE 6 - ROUTE DENSITY
======================================================================

Route density measures how many vehicles use each camera-to-camera route.

Example:

CAM_01 -> CAM_05 = 510 vehicles/hour
CAM_05 -> CAM_09 = 860 vehicles/hour
CAM_09 -> CAM_14 = 310 vehicles/hour

Implementation:

For every consecutive pair in a vehicle trajectory:

routeKey = previousCamera + "->" + currentCamera

Increment route count.

Suggested API:

GET /api/analytics/routes

Output:

[
  {
    "from": "CAM_01",
    "to": "CAM_05",
    "vehicleCount": 510
  }
]

This data should be drawn on Leaflet using thicker lines for higher-density
routes.

currentDensity > normalDensity * 1.5

16. MODULE 11 - ROUTE ANOMALY DETECTION
======================================================================

The problem statement expects suspicious route anomaly alerts.

For the current project, implement this first using deterministic rules.

DO NOT add a heavy AI model immediately.

Recommended anomaly rules:

----------------------------------------------------------------------
16.1 Impossible Travel Speed
----------------------------------------------------------------------

If:

distance / travelTime > configured maximum

Then:

ANOMALY_TYPE = IMPOSSIBLE_TRAVEL

This may also indicate:

- incorrect OCR match
- false plate association
- duplicate plate
- corrupted timestamp

Therefore, the system should mark this as an anomaly for review, not assume
criminal intent.

----------------------------------------------------------------------
16.2 Repeated Route Loop
----------------------------------------------------------------------

Example:

CAM_02
  ->
CAM_07
  ->
CAM_02
  ->
CAM_07
  ->
CAM_02

If repeated more than configured threshold:

ANOMALY_TYPE = REPEATED_ROUTE_LOOP

----------------------------------------------------------------------
16.3 Restricted Zone Rule
----------------------------------------------------------------------

If the project demo includes restricted zones:

IF camera.zone == RESTRICTED

AND plate is not authorized

THEN trigger:

RESTRICTED_ZONE_ENTRY

----------------------------------------------------------------------
16.4 Unusual Time Rule
----------------------------------------------------------------------

Optional demonstration rule:

A vehicle appears repeatedly in a configured zone during a rare time window.

This should be presented as:

"Unusual movement pattern detected"

NOT:

"Criminal vehicle detected"

----------------------------------------------------------------------
16.5 Unexpected Camera Sequence
----------------------------------------------------------------------

If a vehicle appears in two cameras that are geographically unrelated within
an unrealistic time:

Possible anomaly.

This can also help detect OCR mistakes.

----------------------------------------------------------------------
16.6 Configuration File
----------------------------------------------------------------------

Create:

data/anomaly_rules.json

Example:

{
  "maxReasonableSpeedKmh": 180,
  "routeLoopThreshold": 3,
  "routeLoopWindowMinutes": 60,
  "enableRestrictedZones": true
}

======================================================================

Do not immediately migrate the whole project before completing functionality.

29. DEMONSTRATION SCENARIO
======================================================================

For the final demo, configure at least 3-4 cameras.

Example:

CAM_01 - Entry Junction
CAM_02 - Central Junction
CAM_03 - Market Road
CAM_04 - Exit Junction

Scenario:

STEP 1

Vehicle:

TN45AB1234

appears on CAM_01.

System:

- detects plate
- recognizes text
- validates plate
- stores detection

STEP 2

Same vehicle appears on CAM_02.

System:

- matches previous plate
- adds trajectory point
- calculates travel time
- estimates speed

STEP 3

Vehicle appears on CAM_04.

System now displays:

CAM_01 -> CAM_02 -> CAM_04

on Leaflet.

STEP 4

Search TN45AB1234.

Display:

- timeline
- route
- timestamps
- speed
- confidence

STEP 5

Multiple vehicles pass through cameras.

Dashboard updates:

- vehicle count
- density
- route density
- average speeds
- OD matrix

STEP 6

Create artificial congestion in demo data.

Example:

high vehicle count
+
reduced average travel speed

Dashboard marks:

CAM_02 -> CAM_04

as:

HIGH CONGESTION

STEP 7

Put one plate into watchlist.

When detected:

WATCHLIST ALERT

STEP 8

Generate impossible travel data.

Example:

Same plate appears at distant cameras within an impossible time interval.

System displays:

ROUTE ANOMALY / POSSIBLE DATA OR PLATE MISMATCH

This single demo covers almost every major requirement.

30. IMPORTANT TERMINOLOGY FOR PRESENTATION
======================================================================

Use:

"Plate detection precision"

when discussing YOLO detector performance.

Use:

"Exact plate recognition accuracy"

when discussing the complete OCR result.

Do not confuse the two.

Use:

"Estimated average speed between camera nodes"

instead of claiming exact vehicle speed.

Use:

"Rule-based route anomaly"

instead of claiming the system can determine criminal intent.

Use:

"Centralized traffic intelligence"

to describe the complete platform.

33. CONCLUSION
======================================================================

The current project does not need a complete rebuild.

Its strongest components are already in place:

- ANPR
- OCR
- validation
- multi-camera streaming
- GIS
- trajectory tracking
- watchlist alerts

The correct next step is to build the missing CITY-WIDE TRAFFIC INTELLIGENCE
layer on top of the existing detection records.

The architecture should remain modular:

ANPR produces reliable detections.

Trajectory services turn detections into vehicle movement history.

Traffic analytics aggregate those detections into city-wide intelligence.

Alert services monitor watchlists and rule-based anomalies.

Leaflet and the existing dashboard visualize all results.

Following this roadmap allows the project to move toward full alignment with
the problem statement without destabilizing the current working ANPR system.
