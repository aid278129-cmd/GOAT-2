PHASE 1 — PERSPECTIVE / SKEW CORRECTION
=======================================

CURRENT PROBLEM:

License plates captured at approximately 30–60 degree camera angles become trapezoidal.

The detector may correctly locate the plate but OCR then reads distorted characters incorrectly.

Example:

Expected:
`MP42MG2246`

Incorrect:
`MPHMG224`

Implement perspective correction BEFORE OCR.

Desired pipeline:

Vehicle Detection
→ Vehicle ROI
→ Plate Detection
→ Plate Crop
→ Perspective/Skew Analysis
→ Perspective Rectification
→ Image Enhancement
→ OCR
→ Validation

Implement a robust 4-point perspective transformation / homography using OpenCV.

Suggested approach:

1. Receive detected plate crop.
2. Detect plate boundary/corners where reliable.
3. Determine four ordered corner points:
   top-left
   top-right
   bottom-right
   bottom-left
4. Compute perspective transformation matrix.
5. Warp the plate into a flat rectangular image.
6. Correct rotation/skew.
7. Preserve aspect ratio.
8. Pass the corrected image to the existing enhancement/OCR pipeline.

IMPORTANT:

Perspective correction must be confidence-aware.

If reliable plate corners cannot be determined, DO NOT destroy a good crop with an incorrect transformation.

Use:

Original crop
+
Rectified candidate

Run OCR appropriately and select the result with stronger combined evidence such as:

OCR confidence
+
Indian syntax validity
+
temporal consistency.

Save both crops in debug mode:

`original_plate.jpg`
`rectified_plate.jpg`

Add diagnostics:

Perspective correction:
APPLIED / SKIPPED

Estimated skew:
XX degrees

Original OCR:
...

Rectified OCR:
...

Selected:
ORIGINAL / RECTIFIED

Do not remove the existing CLAHE, bilateral filtering, Otsu processing, Tesseract or EasyOCR pipeline unless testing proves a replacement is better.

TEST BEFORE MOVING ON.

Use:

* frontal plate
* moderately angled plate
* heavily angled plate
* two-row Indian plate
* Bharat Series plate

Make sure perspective correction improves angled plates without degrading frontal ones.

PHASE 2 — INTELLIGENT KEYFRAME SELECTION
========================================

CURRENT PROBLEM:

Live cameras produce roughly 10–15 FPS while CPU inference is much slower.

Processing every frame is unnecessary and creates backlog.

Instead of blindly processing frames at fixed intervals, implement intelligent keyframe selection.

Use image sharpness measurement such as:

Laplacian variance.

Pipeline:

Incoming Frames
→ Lightweight Sharpness Analysis
→ Candidate Frame Buffer
→ Select Sharpest Useful Frame
→ ANPR

Example:

Frame A → sharpness 65
Frame B → sharpness 148
Frame C → sharpness 93
Frame D → sharpness 201

Select:

Frame D.

Do NOT send every frame to the Python ANPR service.

Implement a short rolling frame window.

Prefer approximately the sharpest useful frame per second or configurable interval.

Add configuration:

keyframe_selection: true
keyframe_window_ms
minimum_sharpness
anpr_sampling_interval

Avoid selecting frames when:

* extremely blurred
* camera is moving rapidly
* frame is almost identical to recently processed frame

Do not interfere with WebRTC video playback.

The dashboard should remain smooth even while ANPR is processing.

PHASE 6 — MULTI-CAMERA CONCURRENCY
==================================

ANPR processing for one camera must NOT block another camera.

Architecture should behave approximately like:

CAM-01 → Frame Queue → ANPR Worker
CAM-02 → Frame Queue → ANPR Worker
CAM-03 → Frame Queue → ANPR Worker
CAM-04 → Frame Queue → ANPR Worker

BUT:

Do not create unlimited workers on CPU.

Implement bounded queues and sensible concurrency.

VERY IMPORTANT:

If ANPR cannot keep up, DROP OLD FRAMES.

For real-time surveillance:

latest useful frame
is more valuable than
processing a frame from 20 seconds ago.

Therefore:

DO NOT create an ever-growing inference queue.

Suggested behavior:

Camera produces frames
↓
latest-frame buffer
↓
ANPR busy?
YES → replace stale pending frame
NO → process newest suitable frame

Add metrics:

queue depth
frames received
frames sampled
frames processed
frames dropped
average inference latency
camera-specific processing rate
