1. PROJECT OVERVIEW & CORE OBJECTIVES
----------------------------------------------------------------------------------------------------
This project is an end-to-end intelligent traffic surveillance and urban analytics platform developed
for Smart India Hackathon (SIH) under Problem Statement ID 26127 (Bharat Electronics Limited - BEL).

The core objectives are:
  1. Multi-Camera Video Ingestion: Ingest live feeds from IP cameras, RTSP streams, and smartphones
     acting as mobile edge cameras via low-latency WebRTC and Socket.io signaling.
  2. Vehicle & License Plate Detection: Vehicle-first gating (cars, motorcycles, buses, trucks) followed
     by high-precision license plate localization using custom-trained YOLOv8 models.
  3. Indian Registration Standard OCR: Extract license plate characters conforming to Indian Ministry of
     Road Transport and Highways (MoRTH Rule 50) standards (standard rectangular plates, two-row square
     plates, and All-India Bharat Series 'BH' plates).
  4. Perspective & Skew Rectification: Rectify angled/skewed plates using 4-point homography warping
     before OCR to ensure character readability at 30–60 degree camera viewing angles.
  5. Adaptive Temporal Confirmation & Voting: Multi-frame validation with confidence-conditioned frame
     requirements (1 frame for high confidence >=0.85, 2 frames for medium, 3 for lower), guaranteeing
     sub-second confirmation without false positives.
  6. False-Positive Protection: Enforce a strict 6-stage evidence chain guaranteeing zero false positives
     on non-vehicle scenes, road textures, and billboards.
  7. Multi-Camera Trajectory Tracking & GIS: Chronologically stitch vehicle movements across
     geographically distributed cameras on an interactive Leaflet GIS map with travel time estimation.
  8. Watchlist & Stolen Vehicle Hotlist Alerting: Match recognized plates against law enforcement
     watchlists (stolen, expired registration, wanted) with real-time audio-visual dashboard alerts.
  9. Urban Traffic Analytics: Compute vehicle density, congestion metrics, peak flow periods, and
     camera-to-camera movement patterns based exclusively on ground-truth verified detections.


2. CURRENT SYSTEM ARCHITECTURE & COMPONENTS
----------------------------------------------------------------------------------------------------
The platform operates as a distributed hybrid architecture with fine-grained modularity:

A. CORE BACKEND SERVICE (Node.js / Express / Socket.io / WebRTC Signaling)
   - File: `server.js` (Port 3000, HTTPS with auto-generated self-signed SSL/TLS certificates).
   - Functions:
     * Full-duplex WebSocket / Socket.io server for telemetry, detection alerts, and dashboard sync.
     * WebRTC signaling server (SDP offer/answer, ICE candidate exchange) allowing smartphones to stream
       HD camera feeds directly to the dashboard over local Wi-Fi or LAN.
     * Phase 6 Multi-Camera Concurrency Queue Manager (`MultiCameraQueueManager`):
       - Bounded concurrency with worker semaphore (`maxConcurrency: 2` on CPU).
       - Bounded latest-frame queue per camera (depth = 1): drops stale backlogged frames when newer
         keyframes arrive. Newer frames are strictly prioritized for real-time surveillance.
       - Real-time queue metrics: frames received, processed, dropped, queue wait time, inference latency.
     * True Live Latency Telemetry Relay:
       - Preserves and relays frame capture timestamps (`frameCapturedAt`), keyframe selection timestamps
         (`keyframeSelectedAt`), queue wait time (`queueWaitMs`), and round-trip latency (`nodeRoundTripMs`).
     * REST APIs:
       - Watchlist CRUD operations (`/api/watchlist`).
       - Detections feed & history pagination (`/api/detections?limit=50`).
       - Watchlist alert event retrieval (`/api/alerts`).
       - Chronological vehicle trajectory history & GIS segments (`/api/detections/trajectory/:plate`).
       - Urban traffic analytics aggregations (`/api/detections/analytics`).
       - Camera topology configuration (`/api/cameras/config`).
       - Reverse proxy & queue endpoints (`/api/anpr/detect`, `/api/anpr/queue/stats`, `/api/anpr/config`).
     * Smart Deduplication & Manual Scan Bypass:
       - 12-second cooldown (`DETECTION_COOLDOWN`) prevents duplicate logging of the same vehicle on live feeds.
       - `manualScan: true` flag enables operators using the Direct Image Scanner to bypass cooldown for
         instant diagnostic tests.
     * JSON Persistence: Disk backups for detections (`data/detections.json`), watchlist (`data/watchlist.json`),
       and alerts (`data/alerts.json`) with periodic autosave and clean shutdown handlers.

B. ANPR INFERENCE MICROSERVICE (Python 3.14 / FastAPI / PyTorch / ONNX Runtime / YOLOv8 / CRNN / Tesseract / EasyOCR)
   - File: `scripts/anpr_server.py` (Port 5001, HTTP).
   - Multi-stage pipeline:
     * Stage 1 - Vehicle-First Detection: COCO YOLOv8 model detects vehicles (`car`, `motorcycle`,
       `bus`, `truck`) with confidence >= 0.22. Crops vehicle ROI with 5% spatial margin.
       Includes adaptive ROI expansion for two-wheelers/motorcycles where plates sit low on rear mudguards.
     * Stage 2 - License Plate Localization: Trained custom YOLOv8 model (`models/indian_plate_best.pt` /
       `models/indian_plate_best.onnx`) detects plate candidate bounding boxes inside vehicle ROIs
       with confidence >= 0.40. Full-frame fallback disabled by default for strict false-positive gating.
     * Stage 3 - Geometric & Spatial Filtering: Validates plate aspect ratio (1.1 to 6.2 to accommodate
       both MoRTH Rule 50 square plates and standard rectangular plates), minimum dimensions (20x8 px),
       maximum area ratio (<35% of vehicle area), and vertical position (rejects vehicle roof reflections).
     * Stage 4 - Perspective Rectification (Phase 1): Computes 4-point homography and warps tilted crops
       into upright rectangular images. Dual-candidate OCR evaluation tests both original and rectified crops,
       selecting the candidate with higher confidence and syntax validity.
     * Stage 5 - Image Enhancement & Screen Robustness (Phase 5):
       - LAB-space CLAHE local contrast enhancement & glare compensation.
       - Edge-preserving bilateral filtering to suppress LCD subpixel moiré patterns.
       - Adaptive unsharp masking (applied conditionally to degraded crops to avoid stroke distortion).
       - Dual-Otsu binarization (standard dark-on-light and inverted light-on-dark).
     * Stage 6 - HSRP Blue Strip & IND Badge Suppression:
       - Color-based detection in HSV space ($H \in [95, 135]$, $S \ge 50$, $V \ge 40$) in leftmost <= 14%.
       - Masks badge with median plate background color, eliminating false 'IND' prefixes while preserving
         aspect ratio and adjacent state characters intact.
     * Stage 7 - Dedicated CRNN Plate OCR & OCR Decision Router (solution.txt Step 4):
       - Fast dedicated CRNN + CTC model (`models/crnn_plate_best.onnx`, 9.5 ms ONNX inference).
       - Runs first on rectified crops and decodes via Probabilistic Positional Decoding.
       - Decision Router: If CRNN produces a valid MoRTH/BH syntax and confidence >= 0.75 without unresolved
         ambiguity, accepts immediately (`TIER_0_CRNN_ROUTER`) and SKIPS Tesseract and EasyOCR entirely.
       - Only triggers fallback OCR (Tier 1 Tesseract / Tier 2 EasyOCR) when CRNN outputs invalid syntax,
         low confidence (<0.75), or unresolved character ambiguity.
     * Stage 8 - Probabilistic Positional Indian Registration Syntax Decoder (solution.txt Step 6):
       - CTC character emission peak clustering with softmax distribution analysis.
       - Position-dependent character priors and beam search over candidate lattices.
       - Resolves visually confusable characters based strictly on structural slot legality:
         * Pos 0-1 (State Code): Letters enforced ('8'->'B', '0'->'O', '1'->'I', '5'->'S', '2'->'Z').
         * Pos 2-3 (District Code): Digits enforced; handles 1-digit district codes (e.g. DL 3 CBL 1234)
           and 2-digit district codes (e.g. MH 12 AB 1234) without penalizing either valid structure.
         * Series Letters: Letters enforced (e.g. 'DL3C8L1234' correctly resolves to 'DL3CBL1234').
         * Serial Digits: Trailing 4 digits strictly enforced as digits (0-9).
         * Bharat Series Routing: Dynamic validation for 'YY BH #### XX'.
     * Stage 9 - Adaptive Temporal Confirmation Tracker (solution.txt Steps 2 & 3):
       - Adaptive frame requirements based on confidence:
         * High Confidence (>=0.85 with valid syntax): Confirms in 1 frame immediately.
         * Medium Confidence (0.75 - 0.85): Confirms in 2 frames.
         * Lower Confidence (<0.75): Requires 3 frames or rejected.
       - Shortened active confirmation window (6.0 seconds instead of 25.0s) eliminating prolonged delays.
       - Retains 60-second historical tracking window for trajectory aggregation and dashboard analytics.
     * Stage 10 - Dual-Backend Acceleration:
       - Runtime configurable backend (`inference_backend`: `"onnx"` or `"pytorch"`).
       - Fine-grained 10-stage latency profiling recorded on every frame.

C. OPERATOR DASHBOARD & FRONTEND (Vanilla HTML5 / CSS3 / JavaScript / Leaflet.js)
   - Files: `public/dashboard.html`, `public/camera.html`, `public/mobile.html`, `public/js/anpr-engine.js`, `public/css/style.css`.
   - Features:
     * Persistent Single-Page Application (SPA) Matrix: All 5 core modules (Command Center, Vehicle

     * Interactive GIS Leaflet Map: Plots camera nodes, active vehicle trajectories, and animated routes

     * Direct Image Scanner Tool: Allows operators to upload or drag-and-drop static vehicle images for
       instant diagnostic inspection with instant cooldown bypass.

6. CURRENT PROBLEMS & OPERATIONAL CHALLENGES BEING FACED
----------------------------------------------------------------------------------------------------
While the system now operates with sub-second confirmation latency and 92.3% character accuracy on CPU,
the following operational and algorithmic challenges remain for large-scale production deployment:

PROBLEM 1: GPU ACCELERATION FOR 30 FPS MULTI-STREAM PROCESSING (MEDIUM PRIORITY)
  - Current State: All vision and OCR models currently run on CPU. While sub-second confirmation is achieved
    for individual camera dispatches (~1 fps per stream), scaling to 4+ simultaneous 30 FPS HD video streams
    requires dedicated hardware acceleration.
  - Solution Needed:
    * Port YOLOv8 and CRNN backends to NVIDIA CUDA / TensorRT or Intel OpenVINO / DirectML NPU acceleration
      to achieve sub-30ms end-to-end latency per stream.

PROBLEM 2: MOTORCYCLE FRONT-PLATE ABSENCE & REAR SARI-GUARD OBSTRUCTION (MEDIUM PRIORITY)
  - Current State: Many two-wheelers in India lack front registration plates or have vertical stickers
    on curved mudguards that horizontal bounding-box detectors struggle to segment. Rear plates are
    frequently obscured by sari guards, pillion footrests, or luggage ropes.
  - Solution Needed:
    * Train a dedicated two-wheeler multi-view detector that recognizes vertical mudguard sticker plates
      and handles acute upward bracket tilts.

PROBLEM 3: BROWSER HTTPS SELF-SIGNED CERTIFICATES & CLIENT ISOLATION ON VENUE WI-FI (OPERATIONAL)
  - Current State: WebRTC and browser camera access require HTTPS, which currently relies on auto-generated
    self-signed TLS certificates (`cert.pem`, `key.pem`).
  - Operational Note:
    * Mobile devices connecting to `https://<LAN_IP>:3000/camera.html` must bypass the self-signed certificate
      warning once ("Advanced" -> "Proceed to unsafe").
    * Strict venue Wi-Fi networks may enforce "Client Isolation" (AP Isolation), preventing mobile phones
      from reaching the laptop's LAN IP.
  - Recommended Demo Setup:
    * Use a dedicated portable Wi-Fi router or mobile hotspot for the live demo presentation.
    * Optionally launch a Cloudflare or ngrok tunnel with a public signed SSL certificate.

PROBLEM 4: ADVANCED VISUAL VEHICLE RE-IDENTIFICATION (RE-ID) (PHASE 15 ROADMAP)
  - Current State: Trajectory tracking links vehicle journeys across cameras primarily using recognized
    license plate strings (with fuzzy Levenshtein tolerance).
  - Limitation:
    * If a vehicle's plate is completely obscured (mud, physical removal, or severe headlight blooming),
      the vehicle cannot be associated across cameras.
  - Planned Solution (Phase 15):
    * Integrate an OSNet or FastReID deep learning model to extract 512-dimensional appearance embedding
      vectors (color, chassis shape, distinctive stickers/roof racks), enabling appearance-based tracking.

PROBLEM 5: NIGHT-TIME HIGH-BEAM HEADLIGHT GLARE & LOW-LIGHT NOISE
  - Current State: Direct oncoming high beams at night cause CCD sensor blooming, washing out plates mounted
    between headlights.
  - Solution Needed:
    * Deploy physical IR bandpass optical filters and synchronized pulsed infrared illuminators for outdoor feeds.
    * Implement adaptive multi-exposure fusion (HDR) for low-light camera inputs.

PROBLEM 6: STRICT VEHICLE-FIRST GATING ON CLOSE-UP PLATE FEEDS (HIGH OPERATIONAL PRIORITY)
  - Current State: Stage 1 requires COCO YOLOv8 to detect a vehicle (`car`, `motorcycle`, `bus`, `truck`)
    with confidence >= 0.22. In the 180-frame live test, 50 frames (27.8%) were rejected at Stage 1.
  - Root Cause: When operators test by holding mobile phone cameras close to license plates or inspecting
    bumper crops where the vehicle cabin, roof, and wheels are outside the frame, COCO YOLOv8 fails to detect
    a vehicle. With `allow_fullframe_fallback: false`, plate detection is unconditionally bypassed.
  - Solution / Workaround:
    * For desk testing or close-up camera setups: Enable "Allow Full-Frame Fallback" (`allow_fullframe_fallback: true`)
      in dashboard settings or via `POST /api/anpr/config`.
    * For production: Implement a localized bumper/grille anchor detector to complement the vehicle model.

PROBLEM 7: LIVE WEBRTC VIDEO BLUR & SENSOR NOISE DEGRADING PLATE CANDIDATE CONFIDENCE (HIGH PRIORITY)
  - Current State: In the live localhost test, 81 frames (45.0%) detected valid plate candidates, but were
    rejected with `REJECTED_BELOW_PLATE_CONF` because their detector confidence was between 0.20 and 0.39 (below
    the static threshold of 0.40).
  - Root Cause: Live WebRTC video streams suffer from compression artifacts, camera motion, and ambient lighting
    fluctuations that lower the bounding box score compared to static benchmark photographs.
  - Solution:
    * Implement adaptive confidence thresholding for live streaming: Lower `plate_conf_threshold` to 0.28–0.30
      during live video feeds, relying on Stage 4 Indian syntax gating and Stage 5 temporal confirmation to eliminate noise.

PROBLEM 8: CRNN-TO-FALLBACK OCR LATENCY GAP (9.5 MS VS. ~2,200 MS) (MEDIUM PRIORITY)
  - Current State: When CRNN encounters character ambiguity that cannot be resolved by the positional syntax decoder,
    routing to Tier 1 Tesseract or Tier 2 EasyOCR causes frame inference latency to jump from ~10 ms to >2,000 ms
    (e.g. 2,178.7 ms in live frame `cam1_1789492259500`).
  - Impact: Slows down camera frame consumption, delaying consecutive-frame temporal validation.
  - Solution:
    * Impose strict timeout limits (350 ms max) on fallback OCR calls.
    * Expand the Probabilistic Positional Decoder dictionary to resolve common ambiguities without calling fallback OCR.
